1. Objetivo del sistema

El proyecto busca construir una aplicación interna para controlar el desarrollo de packaging, integrando fuentes dispersas y convirtiéndolas en una lectura operativa unificada.

La app no debe limitarse a mostrar datos. Debe detectar qué debería existir, qué evidencia real existe, qué falta, qué está bloqueado y dónde hay inconsistencias.

Objetivo operativo

  • Centralizar estado real de productos y materiales de empaque.
  • Evitar seguimiento manual fragmentado entre Excel, SAP y Moondesk.
  • Detectar faltantes antes de que se vuelvan bloqueos.
  • Dar trazabilidad al proceso completo de packaging.

Objetivo técnico

  • Normalizar fuentes semi-estructuradas.
  • Separar expectativa, evidencia, matching y reglas.
  • Validar comportamiento con fixtures y casos reales.
  • Evitar que una fuente contamine el lifecycle de otra.

3. Modelo conceptual consolidado

El sistema se apoya en una separación conceptual ya validada:

ConceptoSignificadoFuente principal
ExpectativaLo que debería existir para un producto/caso.PM Excel
EvidenciaSeñales reales de que algo ya entró a un circuito operativo.Altas, BOM, SAP, Moondesk, base interna
MatchingProceso de reconciliar expectativa con evidencia.Módulo específico de matching
ReglasInterpretación del estado operativo, score y alertas.project-item-rules.ts y project-rules.ts

Entidad central

La entidad central es project_items. Representa cada componente de packaging dentro de un proyecto. Ya no se interpreta como “material detectado”, sino como un componente esperado o evidenciado dentro de un caso.

Estados clave

CampoUso
componentSlotTipo canónico: ESTUCHE, PROSPECTO, BLISTER, ALUMINIO, etc.
originModeOrigen del item: PM_EXPECTED, REQUEST_DETECTED, BOM_DETECTED, etc.
expectedStatusIndica si el item nace por expectativa, evidencia o no aplica.
identificationStatusNivel de identificación: NOT_IDENTIFIED, PARTIALLY_IDENTIFIED, IDENTIFIED.
matchingStatusCalidad del match: EXACT, INFERRED, AMBIGUOUS, MANUAL_REVIEW.
statusEstado operativo derivado: WAITING_CODE, WAITING_DOCS, BLOCKED, READY, etc.

5. Fuente 1 validada: PM Excel real

1 workbook = 1 caso.
Aunque el archivo tenga varias hojas, se selecciona una sola hoja válida. No se genera una fila staging por cada pestaña.

Reglas del parser PM

  • El archivo PM no es tabular. Es una matriz semi-estructurada con labels y bloques.
  • Se detecta la sheet válida por presencia de Producto + Presentación.
  • Droga Activa se captura cuando existe, pero no bloquea importación.
  • Las hojas vacías o de plantilla se ignoran.
  • Se preserva rawData.rows para parseos posteriores.

Adapter semántico implementado

Se creó un adapter específico para Alta de Mat: alta-mat-material-requests.ts.

  • Lee columnas por posición real, no por header plano.
  • Filtra por contexto de proyecto/token.
  • Clasifica dominio por fila.
  • Distingue PACKAGING_COMPONENT vs PACKAGING_MATERIAL.
  • Opera con matchOnlyExpectedPmItems = true.
  • No crea nuevos project_items; solo enriquece los ya nacidos desde PM.

Severidades

AlertaSeveridad / uso
EXPECTED_COMPONENT_MISSINGINFO en PM-only puro.
CODE_NOT_REQUESTEDWARNING, prioridad alta en primarios.
PRE_BOM_MISSINGWARNING, prioridad alta si afecta estructura operativa.

Estado luego de PM + Altas

  • PRE_BOM_MISSING persiste.
  • APPROVED_DOCUMENT_MISSING persiste.
  • REQUEST_WITHOUT_FORMAL_MATERIAL aparece.
  • El proyecto mejora, pero no puede cerrar.

9. Decisiones de diseño ya tomadas

  • No usar tabla plana para PM.
  • PM gobierna la expectativa.
  • Altas son evidencia temprana, no maestro ni SAP.
  • No crear nuevos project_items desde Alta de Mat en esta etapa.
  • Scope gobernado por PM: matchOnlyExpectedPmItems = true.
  • Separar componente funcional de material del componente.
  • Conservar originMode = PM_EXPECTED cuando una fuente posterior matchea contra un item PM.
  • No subir a IDENTIFIED sin maestro/SAP confiable.
  • Usar parsers/adapters semánticos para planillas reales sucias.
  • Validar cada fuente contra archivo real antes de avanzar a la siguiente.
Regla crítica para próximas fuentes:
No pasar a una fuente nueva hasta haber completado: diseño conceptual → archivo real → mapping real → validación real → commit.

10. Qué queda por hacer

Próxima fuente: BOM / estructura pre-SAP

Es la siguiente fuente lógica porque hoy siguen activas alertas como PRE_BOM_MISSING. Esta fuente debe aportar evidencia de estructura operativa previa a SAP, pero no debe confundirse con SAP formal.

Objetivos de la integración BOM / pre-SAP

  • Entender estructura real de la planilla BOM.
  • Detectar si existe estructura operativa para los componentes esperados.
  • Separar estructura pre-SAP de BOM formal SAP.
  • Resolver o reducir PRE_BOM_MISSING.
  • No crear maestro ni SAP formal desde esta fuente.

Fuentes pendientes posteriores

FuenteObjetivo futuro
Base interna de materialesVerificar existencia de material, plano, especificación, formato, observaciones.
MoondeskTraer tareas, documentos, estados de revisión y aprobación.
SAPConfirmar existencia formal de material, BOM, fase, liberación y fechas.
UI operativa finalMostrar estado real por proyecto, componente, fuente, score y alerta.

Deuda / puntos a vigilar

  • El caso ALUMINIO puede mezclarse con material de blister. Vigilar con más casos reales.
  • El parser de PM detecta lo necesario, pero no conviene expandirlo sin nuevos casos.
  • El parser de Alta de Mat funciona para PYLOBER; validar más adelante con otros productos.
  • La lógica de scoring está calibrada con pocas fuentes. No sobreoptimizar todavía.
  • Evitar que futuros adapters creen project_items fuera del scope PM sin revisión explícita.
