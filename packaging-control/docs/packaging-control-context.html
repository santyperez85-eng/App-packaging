1. Objetivo del sistema

El proyecto busca construir una aplicación interna para controlar el desarrollo de packaging, integrando fuentes dispersas y convirtiéndolas en una lectura operativa unificada.

La app no debe limitarse a mostrar datos. Debe detectar qué debería existir, qué evidencia real existe, qué falta, qué está bloqueado y dónde hay inconsistencias.

Objetivo operativo

  • Centralizar estado real de productos y materiales de empaque.
  • Evitar seguimiento manual fragmentado entre Excel, SAP y Moondesk.
  • Detectar faltantes antes de que se vuelvan bloqueos.
  • Dar trazabilidad al proceso completo de packaging.
  • Reconstruir el lifecycle operativo real de cada componente desde sus evidencias.

Objetivo técnico

  • Normalizar fuentes semi-estructuradas.
  • Separar expectativa, evidencia, matching y reglas.
  • Validar comportamiento con fixtures y casos reales.
  • Evitar que una fuente contamine el lifecycle de otra.

Entidad central

La entidad central es project_items. Representa cada componente de packaging dentro de un proyecto. Ya no se interpreta como “material detectado”, sino como un componente esperado o evidenciado dentro de un caso.

5. Fuente 1 validada: PM Excel real

1 workbook = 1 caso.
Aunque el archivo tenga varias hojas, se selecciona una sola hoja válida. No se genera una fila staging por cada pestaña.

Reglas del parser PM

  • El archivo PM no es tabular. Es una matriz semi-estructurada con labels y bloques.
  • La sheet válida requiere Producto, Presentación y estructura PM operativa real.
  • Se excluyen hojas tipo Forecast, resumen, base, compras, AARR, producción y auxiliares por nombre y por estructura.
  • Droga Activa se captura cuando existe, pero no bloquea importación.
  • Las hojas vacías o de plantilla se ignoran.
  • Caja no significa ESTUCHE; caja queda como empaque terciario/logístico o nota contextual.
  • Se preserva rawData.rows para parseos posteriores.

Derivación de componentes esperados desde PM

ComponentSlotSeñal utilizada

PROSPECTOFila SI/NO marcada positivamente para Prospecto/Info paciente.
BLISTERToggle SI/NO o headers estructurados como Unid. X Blíster / Cant. Blíster.
ALUMINIODescripción material real con aluminio/foil/alu.
FRASCOSolo si hay señal positiva clara; si marca NO, se suprime.

7. Fuente 3 validada: BOM/Recetas fase 1

BOM/Recetas se interpreta como evidencia estructural pre-SAP. No representa SAP formal, maestro de materiales, pedido de código ni aprobación documental.

Alcance de fase 1

  • Trabaja con matchOnlyExpectedPmItems = true.
  • No crea nuevos project_items.
  • No toca MaterialRequest, MaterialsMaster, SapMaterial ni MoondeskTask.
  • Solo resuelve PRE_BOM_MISSING cuando hay cobertura estructural confiable contra un item PM esperado.
  • No resuelve CODE_NOT_REQUESTED, REQUEST_WITHOUT_FORMAL_MATERIAL ni APPROVED_DOCUMENT_MISSING.
  • Si hay múltiples bloques BOM plausibles para el mismo slot PM, no elige por orden: deja revisión manual / confirmación pendiente.
  • Si una señal BOM contradice PM o Altas, debe generar inconsistencia o revisión manual; no sobrescribe datos.
  • Las evidencias BOM usan ProjectItemEvidence.sourceRecordKey compuesto estable generado por el adapter.
  • El componentKey queda como identificador legible interno del item BOM.

8. Lifecycle operativo por project_item

El lifecycle es un read model server-side sobre la información existente. No crea una nueva fuente, no cambia schema y no reemplaza reglas, matching ni scoring.

Qué representa

Reconstruye el estado operativo de un project_item a partir de expectativa PM, evidencias de altas, evidencias BOM/Recetas, alertas, readiness y status persistidos. Su objetivo es explicar dónde está parado un componente y por qué.

Implementación

PiezaDetalle
Serviciosrc/server/services/project-item-lifecycle-service.ts
EndpointGET /api/project-items/:projectItemId/lifecycle
Runnernpm run validate:project-item-lifecycle
AlcanceSolo lectura. No integra SAP, Moondesk, maestro real ni aprobaciones.

Estructura del read model

BloqueUso operativo
milestonesHitos por dimensión: expectativa, pedido de código, estructura pre-SAP, material formal y aprobación documental.
timelineSecuencia operativa normalizada de eventos relevantes.
evidencesEvidencias primarias y secundarias asociadas al item, con fuente, clave trazable y payload resumido.
alertsAlertas abiertas y resueltas que explican bloqueos o avances.
inconsistenciesContradicciones o estados que requieren atención explícita.
reconstructionGapsHuecos donde el estado final es correcto pero falta persistir más detalle para reconstrucción completa.

Orden operativo

  1. PM_EXPECTED define expectativa y scope.
  2. MaterialRequest indica pedido operativo temprano.
  3. BOM/Recetas indica estructura pre-SAP confiable o ambigua.
  4. Material formal, SAP y Moondesk quedan como hitos futuros.
  5. Alertas y readiness explican el estado derivado actual.

Validaciones reales

CasoResultado validado
PYLOBER ESTUCHEExpectativa PM + pedido de código desde Alta de Mat. CODE_NOT_REQUESTED no queda abierto; el item sigue sin estructura pre-SAP ni aprobación documental.
PerPiel Spray FRASCOPM + BOM confiable. El hito pre_sap_structure queda parcial/cubierto por BOM; PRE_BOM_MISSING no queda abierto y aparece la alerta de confirmación pendiente cuando corresponde.
Magnesio FRASCOPM esperado con dos bloques BOM candidatos. No se genera evidencia BOM final, PRE_BOM_MISSING permanece y reconstructionGaps documenta que la ambigüedad de candidatos vive en diagnostics del adapter, no en el item persistido.

Estado luego de PM + Altas + BOM/Recetas fase 1

  • PRE_BOM_MISSING se resuelve solo para items con cobertura estructural BOM confiable.
  • En PerPiel Spray, FRASCO queda cubierto y PROSPECTO sigue pendiente.
  • En Magnesio, FRASCO sigue con PRE_BOM_MISSING porque existen dos bloques BOM candidatos y no hay desempate confiable.
  • APPROVED_DOCUMENT_MISSING persiste.
  • REQUEST_WITHOUT_FORMAL_MATERIAL no se resuelve desde BOM/Recetas.
  • El proyecto mejora, pero no puede cerrar.

11. Decisiones de diseño ya tomadas

  • No usar tabla plana para PM.
  • PM gobierna la expectativa.
  • Altas son evidencia temprana, no maestro ni SAP.
  • BOM/Recetas es evidencia estructural pre-SAP, no SAP formal ni maestro.
  • No crear nuevos project_items desde Alta de Mat en esta etapa.
  • No crear nuevos project_items desde BOM/Recetas en esta etapa.
  • Scope gobernado por PM: matchOnlyExpectedPmItems = true.
  • Separar componente funcional de material del componente.
  • No elegir bloques BOM por orden cuando hay múltiples candidatos plausibles para el mismo slot.
  • CAJA no significa ESTUCHE; caja es empaque terciario/logístico.
  • Conservar originMode = PM_EXPECTED cuando una fuente posterior matchea contra un item PM.
  • No subir a IDENTIFIED sin maestro/SAP confiable.
  • Usar sourceRecordKey compuesto estable para evidencias BOM/Recetas.
  • El lifecycle por item es un read model derivado, no una nueva fuente ni una tabla persistida.
  • Usar parsers/adapters semánticos para planillas reales sucias.
  • Validar cada fuente contra archivo real antes de avanzar a la siguiente.
Regla crítica para próximas fuentes:
No pasar a una fuente nueva hasta haber completado: diseño conceptual → archivo real → mapping real → validación real → commit.

12. Qué queda por hacer

Próximo paso: vista operativa de lifecycle

El read model ya permite consumir estado consolidado por project_item. La siguiente capa debería ser una primera vista simple que muestre milestones, timeline, evidencias, alertas, inconsistencias y reconstruction gaps sin introducir nueva lógica de negocio en UI.

Próximo paso: desempate BOM

Magnesio ya validó el comportamiento conservador ante ambigüedad. El siguiente paso no es crear más items, sino definir cuándo dos bloques/versiones BOM pueden consolidarse o cuándo uno puede ganar de forma confiable.

Objetivos antes de resolver Magnesio automáticamente

  • Definir criterio de selección de bloque/version BOM para productos con múltiples candidatos.
  • Confirmar cómo asociar TAPA, CUCHARA y eventuales accesorios al componente principal sin crear slots nuevos.
  • Validar que Blister NO, Estuche No y Prospecto NO no creen expectativas.
  • Mantener matchOnlyExpectedPmItems = true y evitar duplicados.

Fuentes pendientes posteriores

FuenteObjetivo futuro
Base interna de materialesVerificar existencia de material, plano, especificación, formato, observaciones.
MoondeskTraer tareas, documentos, estados de revisión y aprobación.
SAPConfirmar existencia formal de material, BOM, fase, liberación y fechas.
UI operativa finalMostrar estado real por proyecto, componente, fuente, score y alerta.

Deuda / puntos a vigilar

  • El caso ALUMINIO puede mezclarse con material de blister. Vigilar con más casos reales.
  • El parser de PM detecta lo necesario, pero no conviene expandirlo sin nuevos casos.
  • El parser de Alta de Mat funciona para PYLOBER; validar más adelante con otros productos.
  • El adapter BOM/Recetas fase 1 está validado con PerPiel Jabón, Spray y Magnesio; Magnesio mantiene PRE_BOM_MISSING por ambigüedad real de bloques.
  • El lifecycle reconstruye desde evidencias persistidas. Para casos ambiguos como Magnesio, los detalles finos de candidatos BOM todavía dependen de diagnostics del adapter y no quedan completos en el item persistido.
  • La lógica de scoring está calibrada con pocas fuentes. No sobreoptimizar todavía.
  • Evitar que futuros adapters creen project_items fuera del scope PM sin revisión explícita.
